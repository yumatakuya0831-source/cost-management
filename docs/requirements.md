# 原価管理システム 要件定義書

- 文書版: 1.0
- 確定日: 2026-08-15
- 対象フェーズ: MVP（初版）
- ステータス: 承認済み

## 1. 背景・目的

1店舗で提供するタコス、カレー、コーヒー、アルコール、ソフトドリンクについて、仕入価格とレシピから仕込み原価を算出し、月間販売個数を基準に売上・原価・原価率を可視化する。価格変動による採算悪化を早期に把握し、管理者が根拠のある価格・仕入判断を行える状態を作る。

## 2. 対象範囲・前提

- 対象店舗は1店舗。複数店舗対応は初版対象外。
- 金額は税込で入力・表示する。
- 販売個数とマスタ情報は手入力する。
- 集計期間は暦月単位とする。
- 初期レシピは20人分を基準とし、出来上がり数量は商品ごとに変更できる。
- 在庫、発注、棚卸は初版対象外。購入先、仕入価格、ロット情報は管理する。
- DB、認証、認可にはSupabaseを使用し、ログインにはGoogle OAuthを使用する。

## 3. 対象ユーザー

| ロール | 説明 | 主な権限 |
| --- | --- | --- |
| 管理者 | 店舗運営・原価管理担当者 | 全情報の閲覧、マスタ・販売数・ユーザーの登録更新、秘密レシピの閲覧 |
| 一般ユーザー | 管理者が許可した閲覧者 | ダッシュボードと公開情報の閲覧。更新不可、秘密レシピ閲覧不可 |

未登録または無効化されたGoogleアカウントはログインできない。

## 4. 原価計算仕様

### 4.1 基本式

```text
材料単価 = 税込購入価格 ÷ 購入内容量
ロス反映使用量 = レシピ使用量 ÷ (1 - 仕込みロス率)
材料原価 = 材料単価 × ロス反映使用量
仕込み総原価 = 全材料原価の合計
商品1個あたり原価 = 仕込み総原価 ÷ 出来上がり数量
月間商品原価 = 商品1個あたり原価 × 月間販売個数
月間売上 = 税込販売価格 × 月間販売個数
商品原価率 = 商品1個あたり原価 ÷ 税込販売価格 × 100
月間トータル原価率 = 全商品の月間商品原価合計 ÷ 全商品の月間売上合計 × 100
```

### 4.2 計算規則

- 仕込みロス率は材料ごとに0%以上100%未満で設定する。
- 出来上がり数量は1以上とする。
- 仕入価格は適用開始日を持ち、計算対象月に有効な最新価格を使用する。
- 内部計算では小数を保持し、画面上の金額は1円単位、原価率は小数第1位で表示する。
- 原価計算時点の単価・計算結果を月次スナップショットとして保持する。

## 5. 機能要件（MoSCoW）

### Must

| ID | 機能 | 要件 |
| --- | --- | --- |
| M-01 | Google認証 | Google OAuthでログイン・ログアウトできる |
| M-02 | 許可ユーザー制御 | 管理者が登録したGoogleアカウントだけが利用できる |
| M-03 | ロール制御 | 管理者と一般ユーザーで表示内容・操作権限を分ける |
| M-04 | 商品マスタ | 商品名、カテゴリ、税込販売価格、出来上がり数量、有効状態を管理できる |
| M-05 | 材料マスタ | 材料名、基準単位、仕込みロス率、有効状態を管理できる |
| M-06 | 購入先・仕入マスタ | 購入先、材料、税込価格、1ロット発注数、購入内容量、単位、適用開始日を管理できる |
| M-07 | レシピ管理 | 商品ごとに使用材料、使用量、表示順を管理できる |
| M-08 | 秘密レシピ制御 | 非表示チェックONの場合、一般ユーザーへ材料名・使用量・調合情報を返さない |
| M-09 | 販売実績入力 | 管理者が商品別・月別の販売個数を登録・修正できる |
| M-10 | 原価計算 | 本書の計算式で1個原価、月間原価、原価率を算出できる |
| M-11 | ダッシュボード | 月間売上、トータル原価、平均原価率、販売個数を表示できる |
| M-12 | グラフ | 月別原価率、カテゴリ別売上、商品別原価・原価率を表示できる |
| M-13 | ユーザー管理 | 管理者がユーザーの登録、ロール変更、無効化を行える |
| M-14 | RLS | Supabase RLSで一般ユーザーの更新と秘密レシピ取得を禁止する |
| M-15 | 監査情報 | 登録日時、更新日時、更新者を主要データへ記録する |

### Should

| ID | 機能 | 要件 |
| --- | --- | --- |
| S-01 | 仕入価格履歴 | 過去価格を残し、適用開始日ごとに参照できる |
| S-02 | 再計算 | 価格・レシピ変更後に対象月の原価を再計算できる |
| S-03 | 入力検証 | 負数、0除算、単位不一致、重複登録を防止する |
| S-04 | 目標原価率 | 目標値を設定し、超過商品を強調表示できる |
| S-05 | 操作履歴 | 管理者による主要な登録・変更・無効化を確認できる |

### Could

| ID | 機能 | 要件 |
| --- | --- | --- |
| C-01 | CSV | マスタと販売実績をCSV入出力できる |
| C-02 | データ出力 | 月次集計を帳票またはCSVとして出力できる |
| C-03 | アラート | 原価率や仕入価格の急増を通知できる |

### Won't（初版対象外）

- 在庫数、入出庫、棚卸
- 発注書作成・発注ワークフロー
- POS連携と販売実績の自動取込
- 複数店舗・店舗間比較
- 会計システム連携

## 7. データ要件

- 商品カテゴリ: タコス、カレー、コーヒー、アルコール、ソフトドリンク。追加可能なマスタ方式とする。
- 数量と単位を分離して保持し、少なくともg、kg、ml、L、個、本、杯に対応する。
- 物理削除は原則行わず、有効・無効で管理する。
- 月次販売実績は商品・対象年月の組み合わせを一意とする。
- 過去月の原価を価格変更から守るため、月次原価スナップショットを保持する。

## 8. 非機能要件

### セキュリティ

- 認証済みかつ許可済みユーザーのみ利用可能とする。
- 認可はUIだけでなくServer側とSupabase RLSで実施する。
- Secret Key、service role key、Google Client Secretをブラウザーへ公開しない。
- 秘密レシピは一般ユーザー向けAPIレスポンスに含めない。
- 環境変数実値をGitへコミットしない。

### 性能・可用性

- 通常の主要画面は標準的な回線で3秒以内の初期表示を目標とする。
- 月次ダッシュボードは1店舗、商品100件、販売実績5年分を想定する。
- Supabase障害時はデータ消失を招く再送をせず、利用者へ再試行可能なエラーを表示する。

### 操作性・保守性

- PCとタブレットで主要操作ができ、スマートフォンで閲覧できる。
- 日本語表示とし、金額・年月は日本の形式で表示する。
- 入力エラーは対象項目と修正方法を明示する。
- TypeScript strict、lint、production buildに合格する。

## 9. 受入条件

| ID | 受入条件 |
| --- | --- |
| AC-01 | 許可されていないGoogleアカウントではアプリへ入れない |
| AC-02 | 一般ユーザーはマスタ・販売実績・ユーザーを更新できない |
| AC-03 | 非表示ONの商品は、一般ユーザーの画面・API・直接DB参照の全てで秘密材料と使用量を取得できない |
| AC-04 | 非表示ONでも一般ユーザーは商品名、税込販売価格、計算済み原価、原価率を確認できる |
| AC-05 | 20人分・出来上がり20個のレシピで、仕込み総原価2,000円の場合、1個原価が100円となる |
| AC-06 | 購入価格1,000円、内容量1,000g、使用量100g、ロス率10%の場合、材料原価が端数を保持して約111.11円となる |
| AC-07 | 税込販売価格500円、1個原価150円、月間販売100個の場合、売上50,000円、月間原価15,000円、原価率30.0%となる |
| AC-08 | 仕入価格を更新しても確定済み過去月のスナップショットは自動変更されない |
| AC-09 | 商品・材料・購入先・レシピ・販売実績を管理者が登録・修正できる |
| AC-10 | ダッシュボードのKPI・グラフ・商品別一覧が選択月のデータと一致する |
| AC-11 | `.env.local` がGit管理対象外で、Secret Keyがクライアントバンドルへ含まれない |
| AC-12 | `pnpm lint` と `pnpm build` が成功する |

## 10. 確定事項

- 仕込み原価は材料単価、レシピ使用量、材料別ロス、出来上がり数量から計算する。
- 20人分は初期基準であり、出来上がり数量は商品ごとに変更できる。
- 初版は仕入価格とロット情報を管理し、在庫・発注・棚卸は含めない。
- 秘密レシピでも計算済み原価は一般ユーザーへ表示し、材料名・使用量・調合情報を隠す。
- 秘密レシピ非表示の既定値はOFFで、後から変更できる。

## 11. 未確定事項

要件定義フェーズを止める未確定事項はない。Google OAuthの本番ドメイン、目標原価率の初期値、CSV詳細は各機能の実装時またはShould/Could着手時に確定する。
